TraceGuard · Jira + BigQuery validation

E2E Validation — Architecture

Reads a Jira ticket, works out what to check, writes the SQL, waits for a human to approve it, then runs it in BigQuery and reports back on the ticket.

The Problem

What Are We Solving?

🧩

No Automated Validation

When a BigQuery column, table, or view changed, there was no automated way to verify the change landed correctly in production data.

✍️

High Friction for Engineers

Writing and maintaining validation SQL manually is time-consuming and error-prone — especially across hundreds of tickets and multiple teams.

🔍

No Audit Trail

When a change shipped, there was no shared record of whether it was validated. Stakeholders had no visibility, and compliance had nothing to point to.

Key Features

What Makes It Smart

🧠

NLP Intent Parsing

Understands both structured keywords and plain English. Engineers write naturally — the agent figures out what changed.

"we added a column session_id to the events table" → change_type: column_added → column: session_id
🔍

Partition-Aware Queries

Before generating SQL, the agent checks BigQuery table metadata (zero bytes scanned) to detect partition columns.

sale_date (DAY) detected → WHERE sale_date >= DATE_SUB( CURRENT_DATE(), INTERVAL 7 DAY) No partition found → Warning shown before approval
✏️

Human Query Override

If the generated query needs changes, the reviewer pastes corrected SQL in a Jira comment — the agent uses that on the next run.

1. Agent posts generated query 2. Reviewer pastes {code:sql} fix 3. Reviewer replies: APPROVED 4. Agent uses corrected query
📋

Jira-Native Results

Pass, fail, and errors are posted directly back to the Jira ticket — full audit trail without opening any other tool.

(/) VALIDATION PASSED Details: sale_date total=12842... Bytes scanned: 164.00 bytes (x) EXECUTION_FAILED Error: Reauthentication needed
